## The Gap

When you're writing any code, it's essentially just text. Nothing more, nothing
less. For example,
```python
print("Hello, World!")
```
This line of code is nothing else, but a sequence of characters: `p`, `r`, `i`,
`n`, `t`, `(`, `"`, `H`, `e`, `l`, `l`, `o`, `,`, ` `, `W`, `o`, `r`, `l`, `d`,
`!`, `"`, `)`. To you, these characters and this specific combination means
something. You read `print` and know it means "display something on the
screen", or see `(` and `)` and understand these are a part of a function call.
This is not the case with computers. They don't directly understand what these
characters and this specific combination mean, we've covered this in
[week 1's markdown](./W01-intro.md), but we didn't explicitly talk about how 
this "gap" is filled. Before we start filling that gap, let's do a little recap
of what do we mean by computers not understanding these.

A CPU is just an over-powered and over-engineered addition machine. It only
understands `0`s and `1`s, and how to do logic operations and addition. If you
remember we've discovered there are some ways of representing (e.g. texts,
images, videos, sounds) a lot of stuff. Now we will fill the gap between your
source code and the execution with this markdown.

## The Interpreter's Job: Translator and Executor

The Python interpreter is a specialized computer program. Its fundamental role
is to directly read and execute your Python code line by line. It effectively
bridges the gap between your human-readable instructions and the computer's
underlying hardware. To bridge this gap, the interpreter performs a translation
function.

### Translator

Think of the interpreter as a highly specialized linguist. It takes your Python
source code as input, which as we've discussed is just a text file full of
characters, and translates it into a language that the computer can eventually
process. Don't confuse this with compiling, interpreter doesn't directly
translates your code word-for-word into raw 0s and 1s right away. Instead, it's
a multi-stage process, which we'll explore in detail later, involving turning
your code into `tokens`, then a structured `Abstract Syntax Tree`, and finally
`bytecode`.

The key is that the interpreter can *understand* the rules of Python syntax and
semantics, also it ensures that your instructions are correctly converted into
a form the underlying machine can execute.

### Executor

The interpreter doesn't just translate and then hand off the job. It actively
runs the translated instructions. Basically, it's analogous to the heart, it
brings your code to life. Once the translation into a lower-level form (e.g.
bytecode) phase has finished, interpreter immediately starts executing those
instructions. This immediate translation and execution is characteristic of
interpreted languages like Python. As the executor, it manages your program's
flow, calls functions when needed, performs calculations using your CPU,
handles I/O, and manages memory. It's the active environment where your program
performs its actions.

Basically speaking, the Python interpreter is the software that reads your
text-based Python source code, figures out what you want the computer to do,
then runs those instructions. We'll dive into how does it figure out what to do
when it's just presented with a `continuous stream of characters`, so to say,
which brings us to a crucial step in understanding your code: smashing it into
pieces.

## Why Break Down Code?

OK, now that we've understood what the Python interpreter's job is, you should
be wondering how it actually starts figuring out your code. It's not magic lol,
and it certainly can't understand your program as one long, continuous piece of
text. Interpreter needs to systematically break down your code into smaller,
manageable chunks before it can do its job.

### Continuous Stream vs. Meaningful Chunks

The main challenge with figuring out code is, when you write Python code, even
if it looks neatly organized to you with`print`, `if`, `else`, `x = 10`, etc.,
the computer initially sees it as nnothing more than a continuous stream of
characters.

Take a closer look at our [previous example](#the-gap). To you, it's an
unbroken string of letters, numbers, and symbols. We intuitively segment this
into distinct words and symbols based on our knowledge of the language. We
recognize `print` as a function call, `(` and `)` as a delimiter, and
`"Hello, World!"` as a string literal.

A computer, as we've discussed in [W01](./W01-intro.md), doesn't possess this
innate understanding. It doesn't directly know where one `meaningful unit` ends
and another one begins. It needs a very systematic way to break down this
`continuous stream of characters` into `discrete`, `recognizable`, and
`meaningful` chunks.
