## The Gap

When you're writing any code, it's essentially just text. Nothing more, nothing
less. For example,
```python
print("Hello, World!")
```
This line of code is nothing else, but a sequence of characters: `p`, `r`, `i`,
`n`, `t`, `(`, `"`, `H`, `e`, `l`, `l`, `o`, `,`, ` `, `W`, `o`, `r`, `l`, `d`,
`!`, `"`, `)`. To you, these characters and this specific combination means
something. You read `print` and know it means "display something on the
screen", or see `(` and `)` and understand these are a part of a function call.
This is not the case with computers. They don't directly understand what these
characters and this specific combination mean, we've covered this in
[week 1's markdown](./W01-intro.md), but we didn't explicitly talk about how 
this "gap" is filled. Before we start filling that gap, let's do a little recap
of what do we mean by computers not understanding these.

A CPU is just an over-powered and over-engineered addition machine. It only
understands `0`s and `1`s, and how to do logic operations and addition. If you
remember we've discovered there are some ways of representing (e.g. texts,
images, videos, sounds) a lot of stuff. Now we will fill the gap between your
source code and the execution with this markdown.

## The Interpreter's Job: Translator and Executor

The Python interpreter is a specialized computer program. Its fundamental role
is to directly read and execute your Python code line by line. It effectively
bridges the gap between your human-readable instructions and the computer's
underlying hardware. To bridge this gap, the interpreter performs a translation
function.

### Translator

Think of the interpreter as a highly specialized linguist. It takes your Python
source code as input, which as we've discussed is just a text file full of
characters, and translates it into a language that the computer can eventually
process. Don't confuse this with compiling, interpreter doesn't directly
translates your code word-for-word into raw 0s and 1s right away. Instead, it's
a multi-stage process, which we'll explore in detail later, involving turning
your code into `tokens`, then a structured `Abstract Syntax Tree`, and finally
`bytecode`.

The key is that the interpreter can *understand* the rules of Python syntax and
semantics, also it ensures that your instructions are correctly converted into
a form the underlying machine can execute.

### Executor

The interpreter doesn't just translate and then hand off the job. It actively
runs the translated instructions. Basically, it's analogous to the heart, it
brings your code to life. Once the translation into a lower-level form (e.g.
bytecode) phase has finished, interpreter immediately starts executing those
instructions. This immediate translation and execution is characteristic of
interpreted languages like Python. As the executor, it manages your program's
flow, calls functions when needed, performs calculations using your CPU,
handles I/O, and manages memory. It's the active environment where your program
performs its actions.

Basically speaking, the Python interpreter is the software that reads your
text-based Python source code, figures out what you want the computer to do,
then runs those instructions. We'll dive into how does it figure out what to do
when it's just presented with a `continuous stream of characters`, so to say,
which brings us to a crucial step in understanding your code: smashing it into
pieces.

## Why Break Down Code?

OK, now that we've understood what the Python interpreter's job is, you should
be wondering how it actually starts figuring out your code. It's not magic lol,
and it certainly can't understand your program as one long, continuous piece of
text. Interpreter needs to systematically break down your code into smaller,
manageable chunks before it can do its job.

### Continuous Stream vs. Meaningful Chunks

The main challenge with figuring out code is, when you write Python code, even
if it looks neatly organized to you with`print`, `if`, `else`, `x = 10`, etc.,
the computer initially sees it as nnothing more than a continuous stream of
characters.

Take a closer look at our [previous example](#the-gap). To you, it's an
unbroken string of letters, numbers, and symbols. We intuitively segment this
into distinct words and symbols based on our knowledge of the language. We
recognize `print` as a function call, `(` and `)` as a delimiter, and
`"Hello, World!"` as a string literal.

A computer, as we've discussed in [W01](./W01-intro.md), doesn't possess this
innate understanding. It doesn't directly know where one `meaningful unit` ends
and another one begins. It needs a very systematic way to break down this
`continuous stream of characters` into `discrete`, `recognizable`, and
`meaningful` chunks.

The process of handpicking those `meaningful chunks` from that continuous
stream of characters is the very first analytical step the interpreter takes in
understanding source code. Not breaking down your code would be analogous to a
person trying to a read a book with no spaces, no punctuation, and no word
boundaries. Just a jumbled up mess, and it would be a nightmare to read and
understand fully.

### The Analogy of Human Language

To understand this concept of breaking down code into smaller chunks, we need
to understand how language works in the first place.

Look at an example: `The quick brown fox jumps over the lazy dog.` As a human,
you don't perceive this sentence as a continuous string of 44 individual
characters, your brain automatically performs a process similar to what the
interpreter does. Let's look at it step-by-step.

1. Identify Words: You see "The", "quick", "brown", etc. These are the
meaningful units or "tokens".
2. Identify Punctuation: You recognize the period `.` at the end as a
distinct symbol indicating the end of the sentence.
3. Ignore Irrelevant Separators: Your brain automatically process the
spaces between words, using them as delimiters, but they don't carry actual
meaning themselves; they just separate the words.

Words are analogous to `tokens`. They are fundamental building blocks that,
when put together according to grammatical rules, form a complete and
meaningful sentence, or in our case, source code.

The interpreter's job when reading your source code, is quite similar. It has
to take that raw stream of characters, perform the equivalent oof identifying
"words" or "punctuation" specific to Python, and discard things like extra
spaces and other irrelevant characters (unless they're significant, like in
identation).

This first step, "handpicking" so-to-say, of meaningful chunks is what allows
both humans and the interpreter to begin to understand the structure and intent
behind a continuous stream of characters.

# Lexical Analysis: Identifying Building Blocks (Tokens)

OK, we've understood why the interpreter needs to break down your code into
pieces. Let's dive into **how**. In this initial phase, the interpreter
executes something called **lexical analysis**. It's the process where the raw
source code is transformed into fundamental building blocks that the rest of
the interpreter can understand: **tokens**.

## What Are Tokens?

Tokens are, basically speaking, the smallest, individual, meaningful unit in a
programming language that has a specific, well-defined meaning to the
interpreter. As we've discovered, these are analogous to words. It's no longer
just random characters like `p` or `(`, but a recognized piece of the
language's vocabulary. When the interpreter looks at the source code, it
doesn't see a bunch of characters, but sees a sequence of these tokens.

A token itself is not just text, it carries a small package of information,
too. Generally speaking, every token has two main parts:

1. **Token Type (Token Category):** This information tells the interpreter what
kind of thing the token actually is. Is it a command (e.g. `print`, `if`), a
number (e.g. `10`, `3.14`), or is it an operator (e.g. `+`, `-`, `=`)?

2. **Lexeme (Value):** This is the exact sequence of characters from your
original code that forms this particular token, the actual text. It's what the
lexer (which we'll get to in a minute) found, as a literal string.

For example,
```python
print("Hello, World!")
```
is not just a string of letters to the interpreter, because they get converted
into something like `TOKEN(TYPE: KEYWORD, LEXEME: "print")`.

Tokens are incredibly important because they **are** the bridge between the raw
source code and the interpreter's understanding of that source code. Let's try
to understand the role of tokens in the interpreter's pipeline.

> **Output of Lexical Analysis**
> The job of the lexical analysis phase is to break down your code into these
> tokens, reading the source code line by line.

> **Input for the Next Stage**
> Once the lexer is done, next part of the interpreter, called the parser,
> doesn't have to deal with messy raw characters anymore. Instead it works
> directly with this neat and structured token stream, which makes the job of
> the parser much more easier.

> **Stripping Unnecessary Information**
> One of the most important things the lexer does, is that it effectively
> discards information that isn't directly meaningful to the computer's
> execution. This primarily includes most `whitespace` (e.g. extra spaces
> between words, tabs, newlines) and `comments`; however, remember that
> Python's significant identation is an exception here. The lexer does process
> and generate special tokens for identification levels, because it's
> fundamental to Python's syntax, unlike many other languages. These are
> important for human readability but only makes things worse for the parser.
> So they shall be gone.

## The Lexer/Scanner: Lexical Analysis

The lexical analyzer (a.k.a. the lexer, scanner, tokenizer) is the part of the
interpreter that's responsible for finding and producing tokens. You can think
of it as the interpreter's eyes and ears, systematically reading your code and
tearing it part into tokens. The Python lexer is called `tokenizer`.

> **Its Input:** The tokenizer's input is the raw, continuous stream of
> characters that we've talked about, which come directly from your Python
> source code file (`.py` files).

> **Its Output:** The tokenizer's output is not more text, mind you; it's a
> structured stream (or sequence) of tokens. Each token is neatly packaged with
> its type and its lexeme.

Let's see how it works in detail.
- The Python tokenizer reads your code from left to right, top to bottom.
- It checks the source code for predefined rules to determine where one token
ends and the next one begins.
- If it finds a valid sequence of characters that forms a valid token according
to its rules, it packages those characters into a `token object` (e.g.
`TOKEN(TYPE: KEYWORD, LEXEME: "print")`), and adds it to the output stream.

### The Interpreter's Processing Pipeline

When we talk about the execution of source code, we usually think of it as some
kind of a `pipeline` (a.k.a. `assembly line`), because the interpreter
processes the code in a series of stages, and each stage has a specific role.
That's why it's often called the pipeline, because your code flows through each
stage, getting transformed and refined at each step. The tokenizer is the first
stage in this processing pipeline.

The stages in the Python interpreter's processing pipeline are as follows:
1. Lexical Analysis (Tokenizer)
2. Parsing (Parser)
3. Compilation to Bytecode (Compiler)
4. Execution (Python Virtual Machine, a.k.a. PVM)

This pipeline ensures that your code is systematically analyzed, understood,
and prepared for execution.

### Tokenizer's Role in the Pipeline

Building on the pipeline analogy, tokenizer occupies the very first stage of
it. It's the starting point of the source code execution. Its primary role is
to take your code in its most "raw" form, and transform it into something that
is computer-readable. It takes your source code text, and transforms it into
the tokens we've talked about. To remind you, the reason why it does that is
because it needs to prepare your code for the next stage, the parser. The
parser needs context, not just text. Without the tokenizer, the parser wouldn't
have the structure to build upon. The tokenizer also acts as an essential
filter, as we've talked before. It discards stuff that isn't useful for the
code's execution.

To sum it up, the tokenizer has an irreplacable role of translating the
human-friendly, yet machine-readable, source code text into the first
`machine-processable` format that the rest of the pipeline can build upon.

that this is literally the end of the code. That is ***not*** an actual
character in your source code, it's put explicitly by the tokenizer there.

## How Whitespaces are Handled?

The tokenizer handles whitespaces (e.g. space characters ` ` and tabs `    `)
with some rules.

- **General Rule:** Most of the time, the tokenizer uses spaces and tabs as
delimiters between tokens. Once a token is identified, the whitespace that is
separating it from the next token is usually discarded. You can think of it as
the spaces between words.

- **Exception 1 - Inside String Literals:** Whitespaces that appear inside
string literals, which we'll look at an example in minute, are preserved. They
are considered to be a part of the string token's lexeme, and are not
discarded. Now, let's see an example of that.

```python
print("Hello, World!")
```
This is our code snippet before the tokenizer does its job.
```text
TYPE: NAME       LEXEME: 'print'            (Starts at: 1:0, Ends at: 1:5)
TYPE: OP         LEXEME: '('                (Starts at: 1:5, Ends at: 1:6)
TYPE: STRING     LEXEME: '"Hello, World!"'  (Starts at: 1:6, Ends at: 1:21)
TYPE: OP         LEXEME: ')'                (Starts at: 1:21, Ends at: 1:22)
TYPE: NEWLINE    LEXEME: '\n'               (Starts at: 1:22, Ends at: 1:23)
TYPE: ENDMARKER  LEXEME: ''                 (Starts at: 2:0, Ends at: 2:0)
```
And this is the output of the tokenizer (formatted for readability). As you can
see the space character (` `) between the characters `,` and `W` is not
discarded, because it's a part of the string's lexeme.

- **Exception 2 - Inside Comments:** Whitespaces that appear inside comments
are also preserved.

```text
TYPE: NEWLINE        LEXEME: '\n'                      (Starts at: 8:30, Ends at: 8:31)
TYPE: ENDMARKER      LEXEME: ''                        (Starts at: 9:0, Ends at: 9:0)
```
As you can see, after the line `print(f"i is now 2")`, there is only a single
`token.DEDENT`, because we're still in the for loop, but we're no longer in the
if statement. That is precisely why there is 2 `token.DEDENT`s after the line
`print(f"i is not 2")`, because we're no longer in the else statement or the
for loop. Also, you should see that the lexeme of a double indentation is
literally a double indentation, which is a double tab character (`   `) in our
case.
